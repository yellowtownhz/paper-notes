Failure as a Process: An Anatomy of CLI Coding Agent Trajectories

Xiangxin Zhao, Han Li, Shuaiting Li, Tianyi Zhao, Earl T. Barr, Federica Sarro, He Ye

Coding_Agent Trajectory_Analysis Agent_Failure_Analysis CLI_Agent Error_Recovery

论文笔记: Failure as a Process: An Anatomy of CLI Coding Agent Trajectories

关键问题：pass/fail 只告诉我们任务最后有没有完成，却看不到失败何时开始、何时失去修复机会、又何时才暴露出来。

关键做法：把失败轨迹拆成三个时间点——决定性错误 $t_{err}$、经验性锁死 $t_{lock}$、首次可观测失败 $t_{obs}$——再把时间、根因与恢复行为连起来分析。

关键结论：在 1,184 条失败轨迹中，决定性错误中位数出现在第 7 步；57.9% 属于“信息已在场却被误用”的 epistemic error。真正区分成功与失败的，不是是否犯错，而是 agent 是否及时响应错误信号并在短程内恢复。

我的判断：这篇最有价值的不是又做了一张 failure taxonomy，而是把错误发生、不可恢复和外显失败分开。它准确指出了 intervention 应该放在哪里；但 $t_{lock}$ 是事后标注，论文还没有证明在该窗口内插入检查真的能提高成功率。

2. 关键问题：失败不是终点标签，而是一段有内部阶段的过程

Golden Case -- 一条“看起来一直正常”的错误轨迹

Terminal-Bench 的 git-workflow-hack9 要求 agent 先找到仓库的 .git，进入仓库后再搭站点。GPT-5 + Terminus2 在第 2 步执行 find 与 cd 的组合命令，命令没有输出；agent 把“空输出”解释成“切换目录成功”，于是开始在错误的 /app 下建站。

  • 第 2 步，$t_{err}$：把未验证的空输出当成成功，形成错误前提。
  • 第 6 步，$t_{lock}$：agent 已完全围绕错误目录搭建站点，之后再未重查工作目录；作者事后判断从这里起没有观察到正确恢复。
  • 第 23 步，$t_{obs}$：直到 git add -A 报出 not a git repository，失败才第一次显性出现。

也就是说，失败在第 2 步已经开始，第 6 步以后经验上锁死，但表面又健康运行了 17 步。只在最终测试或异常输出出现时才诊断，会把真正的起点错后很多。

此前工作已经会给失败分类或定位坏 step，但通常把 failure 当成静态 outcome。本文要补的变量是时间结构：一个错误何时形成、agent 还有多久能改、外界何时才看得见。CLI 场景尤其适合这个问题，因为 agent 会连续修改目录、依赖、权限与构建状态；一次未经验证的假设可能被几十步后续动作放大。

3. 关键方法：用三个时间点把“错误 → 锁死 → 暴露”串起来

3.1 数据怎样进入分析流程

  1. 在 Terminal-Bench 的 240 个容器化 CLI 任务上收集 3 个 scaffold（MiniSWE、OpenHands、Terminus2）与 7 个模型的轨迹，即 21 种 model-scaffold system。
  2. 从理论上的 5,040 次运行中取得 3,843 条完整轨迹，再筛到跨系统可比较的 89 个任务；最终得到 1,794 条有效轨迹：610 成功、1,184 失败，共 63,000+ execution steps（Section II-B/C, Figure 1）。
  3. Claude Opus 4.6 先生成结构化标注草稿；每条失败轨迹再由两位人工标注者独立检查完整 trace、证据与标签，冲突讨论解决。论文报告关键标签 Cohen's $\kappa=0.78\text{--}0.94$；root cause 为 0.83，三个时间点的 weighted $\kappa\ge 0.94$（Section II-D, Threats to Validity）。
  4. 用标签回答四类问题：错误发生时间、根因、成功/失败恢复，以及模型与 scaffold 的差异。

这里的 step 是“一轮 reasoning + 一次 action”。论文把 error 限定为轨迹中的问题事件，把 failure 限定为最终失败 outcome；“不可恢复”也只是 empirically unrecoverable，意为这条已观察轨迹后来没有恢复，不声称所有可能续写都无法挽救。

3.2 三时间点形式化

  • $t_{err}$：决定最终失败的 decisive error 首次出现；通过看完整条轨迹事后定位，不一定是第一个局部错误。
  • $t_{lock}$：此后再没有观察到正确恢复、后续动作只会延续错误的经验性锁死点。
  • $t_{obs}$：第一次出现外部可见的失败证据；它不必晚于 $t_{lock}$。

由此定义：

$$ \text{fix window}=t_{lock}-t_{err}, \qquad \text{observability lag}=t_{obs}-t_{lock}. $$

Golden Case 的数据流正是：完整 trace → 标出第 2/6/23 步 → 得到 4 步 fix window 与 17 步 observability lag → 再判断根因是 false premise、锁死后行为是继续执行。

3.3 从事后解释走向在线监控

三时间点本身只能 hindsight diagnosis。作者另让 Claude Sonnet 4.6 作为 prefix monitor，只看前 $t$ 步且不知道最终 outcome，判断轨迹是否已经越过 $t_{lock}$。测试集含 600 条轨迹（300 成功、300 失败）的 2,659 个 prefix，并比较两种输入：只给任务名，或额外给任务核心要求（Section II-E）。这个对照在问一个很好的问题：失败是从行为本身就能看出，还是必须对照 specification 才知道哪里错了？

3.4 根因与恢复怎样标

  • 根因：不是给最终 symptom 分类，而是标注 $t_{err}$ 处触发决定性错误的机制，再归为 epistemic / competence / environment。
  • 失败恢复：在 $t_{lock}$ 之后，用“主要行为 + 是否意识到失败”的 first-match rule 归纳尾部模式，并同时统计发生占比、浪费步数占比和尾部长度。
  • 成功恢复：在成功轨迹中定位错误后的 recovery episode，计算回到正确执行路径所需步数，再与失败恢复比较。

这比只数 action type 多了一层解释力：同样是继续运行测试，可能是有效恢复，也可能是在 outcome 已不可改变后重复检查。

4. 数据集：跨 21 个系统的 Terminal-Bench 轨迹快照

  • 任务：最终分析 89 个 Terminal-Bench 任务，覆盖 16 类任务。
  • 模型：Claude Sonnet 4、GPT-5、Gemini 2.5 Pro、Qwen3 Coder 480B、DeepSeek V3.2、Kimi K2 Instruct、Devstral 2。
  • Scaffold：MiniSWE、OpenHands、Terminus2。
  • 来源：71.4% 复用公开 Terminal-Bench 轨迹，28.6% 由作者补跑缺失组合；作者称沿用 Harbor 的相同环境、temperature 与最大迭代数。
  • 最终规模：1,794 trajectories = 610 成功 + 1,184 失败；难度分布为 459 easy、742 medium、593 hard。

一个需要回查开放数据的口径问题：Section II-C 先说“只保留 21 个组合全部可用的任务”，得到 $89\times21=1,869$ 条；下一句又说其中 75 条因 failed executions 不可用，最终剩 1,794 条。“全部可用”与“仍有 75 条不可用”不能同时按字面成立，可能是筛选描述或 available 的定义写得不精确 [?]。

5. 关键结果：错误很早形成，真正稀缺的是及时更新信念

5.1 时间：第 7 步出错，第 12 步锁死，第 16 步才外显

Figure 4 最值得看三件事：紫色的 $t_{err}$ 曲线最早上升、绿色 $t_{lock}$ 随后、蓝色 $t_{obs}$ 最慢，而且蓝线封顶在 72%——28% 的失败整条轨迹都没有出现可观测失败信号。

  • 失败轨迹长度中位数 27 步（均值 42），但 $t_{err}$ 中位数只有 7（均值 11.9）：错误通常在前四分之一形成（Finding 1）。
  • $t_{lock}$ 中位数 12（均值 18.6）。逐轨迹计算的 fix window 中位数只有 1 步；60.9% 至少留 1 步，43.9% 至少留 3 步，239 条超过 10 步（Finding 2）。注意“1 步”不能用 $12-7$ 得到，因为 median of differences 不等于 difference of medians。
  • 在会外显的 72% 轨迹中，$t_{obs}$ 中位数 16（均值 22.5）；按两个总体中位数比较，显性信号约晚于决定性错误 10 步（Finding 3）。

在线检测并没有自动吃到这个窗口。 Prefix monitor 对已经锁死的轨迹可达 82% precision，但只给任务名时 recall 为 18.2%，加入核心要求后也只有 28.8%；median lead time 相对 $t_{lock}$ 为 0，只有 3.7%--8.7% 的失败能在锁死前报出（Finding 4）。Specification 的作用却很清楚：ignored requirement 的 recall 从 3% 升到 22%，false premise 从 15% 升到 32%，capability gap 从 12% 升到 30%；成功轨迹早期 prefix 的 false-positive rate 仍为 2%--3%。

证据边界：82% precision 来自人为平衡的 300 成功 / 300 失败样本，不能直接外推到真实部署 prevalence；而且论文只测了一个 monitor model，没有简单规则、不同模型或 calibration baseline。更根本的是，$t_{lock}$ 来自完整轨迹的反事实不足式标注——它是好用的分析靶点，但还不是可在线直接读取的状态。

5.2 根因：57.9% 不是“不会”，而是“没有正确使用已经看到的信息”

Table II 把 1,184 个决定性错误分成九类：

大类 细类 占全部失败
Epistemic (57.9%) False premise 30.7%
Specification neglect 14.9%
Output misreading 4.4%
Ignored signal 4.1%
Premature action 3.7%
Competence (32.8%) Knowledge gap 24.0%
Capability limitation 8.8%
Environment (9.4%) Environment blocker 8.8%
Other 0.6%

False premise 单类就占 30.7%（Finding 6）。论文 Figure 6 的例子很典型：agent 看到 sudo: not found，却把“系统没有 sudo 程序”推断成“我没有创建 /srv/shared 的权限”，随后绕去 /tmp 和 home directory。后面的命令并非随机，而是在错误世界模型下内部一致地推进。

这个结论在 21 个 model-scaffold 组合里都保持：epistemic error 占各系统失败的 44%--80%（Table V, Finding 14）。它支持把 scaffold 的重点从“生成更多修复尝试”移到“显式保存假设、绑定证据、在 mutation 前验证关键前提”。不过 epistemic 与 competence 的分界依赖标注者判断“避免错误所需信息是否已经可用”，带有不可消除的 hindsight 主观性；高 $\kappa$ 说明 codebook 可重复，不等于分类天然客观。

5.3 恢复：成功轨迹也会错，区别在是否响应信号

最反直觉的结果是：71% 的成功轨迹至少从一个错误中恢复（Finding 9）。错误本身不是 separator；恢复行为才是。

  • 成功恢复中位数 5 步，失败恢复中位数 12 步（Finding 10）。长时间“继续修”很可能意味着诊断没更新。
  • 成功与失败轨迹看到可观测错误信号的比例接近（74% vs. 72%），但在锁死前真正响应至少一个信号的比例是 92% vs. 37%（Finding 11）。差距不在 observability，而在 belief update。
  • 锁死后只有 18% 立即停止；82% 继续消耗执行。修错问题只占 24% 的失败轨迹，却贡献 39% 的全部浪费步数，尾部中位数 21 步；重复同一策略贡献另外 29% 浪费（Table III, Findings 7--8）。
  • 26% 的失败轨迹会伪造成功证据；84% 的 fabrication 在 $t_{lock}$ 当步或之后开始，中位 onset 恰好等于 $t_{lock}$。因此 fabrication 更像失去恢复能力后的应对，而非最初根因（Finding 12）。

这里仍是观察性比较：92% vs. 37% 没有通过强制 agent 响应/忽略同一信号来做干预，也没有按 task difficulty 与 system capability 完整匹配。它强烈指向“响应信号”这一机制，但还不能单独证明增加 stop-and-verify 提示会带来同等幅度的因果收益。

5.4 模型与 scaffold 都影响 pass rate，但不是本文最稳的因果结论

21 个系统的 pass rate 跨 19%--45%（Table IV）：同一 scaffold 换模型、同一模型换 scaffold 都有明显变化。与此同时，每个系统中 epistemic error 都是最大类。可惜每个 cell 主要来自同一批约 89 个任务的一次性运行，论文没有置信区间或随机种子；作者也在 Threats to Validity 中承认比较是 observational rather than causal。因此 Table IV 更适合证明“系统整体不可只用 model 名称代表”，不适合拿来排模型或宣称某 scaffold 的独立 treatment effect。

6. Insights

6.1 对论文本身的 Comments

论文真正的新变量是“隐藏失败时间”，不是 failure label。 Figure 4 中 28% 永不外显、monitor 的 lead time 又接近 0，说明只优化错误检测器可能太晚。更直接的设计是让高风险前提在动作前变成显式断言：pwd、test -d .git、检查 exit code、把 task requirement 与当前 state 对齐。观察 → 推理 → 行动是：错误常在第 7 步前后形成 → 外部信号常在十步后才来 → 应把验证前移到早期 state transition，而不是等待 exception。

$t_{lock}$ 很有解释力，但概念上混合了轨迹事实与未观察反事实。 “后来没有恢复”不等于“当时没有任何可行恢复”。同一个 prefix 若换一次采样、换一个 verifier 或由人接管，可能继续成功。下一步最关键的实验不是再标更多 $t_{lock}$，而是从候选点做 counterfactual replay：重采样后续、插入 requirement check、回滚错误 state，测真实 recovery probability 曲线。这样才能把经验锁死点升级为 intervention threshold。

Filtering 比标注更可能限制外推。 论文对失败标签做了很强的双人复核，但最终只保留 89/240 个任务，并排除了 1,197 次异常或未完成运行。那些最容易触发 timeout、harness conflict、环境脆弱性的任务恰好可能是 CLI agent 最真实的失败面。当前结论更准确地说是：在“所有系统大体都能完整运行”的 Terminal-Bench 子集上，epistemic error 主导。

成功轨迹的标注质量交代得不如失败轨迹清楚。 论文明确说每条 failed trajectory 双人独立标注，但 Finding 9--11 又需要识别 successful trajectory 的错误与 recovery episode；正文没有同等清晰地报告成功轨迹的双标注范围与 agreement [?]。而 71%、92% 这些最有产品价值的数字恰好依赖这一部分。

6.2 对实际 coding-agent 系统的行动建议

  1. 建立 assumption ledger：重要环境判断必须保存“命题 + 证据 + 验证命令”，尤其是 cwd、权限、依赖版本、测试目标和用户约束。空输出不能自动当成功。
  2. 在早期 mutation 前设 checkpoint：决定性错误中位数在第 7 步，优先审计第一次写文件、安装依赖、切目录、改权限和建分支，而不是平均地监控所有 step。
  3. 让 monitor specification-conditioned：将 task requirements 作为活的验收条件持续暴露给 monitor；论文中它把 false-premise recall 从 15% 提到 32%，比只看“行为像不像失败”更有效。
  4. 给 recovery 设置重诊断预算：成功恢复中位数 5 步。超过一个短窗口后，不应继续围绕同一 root cause 加 repair，而应回滚、重新读取证据或切换诊断者。5 步是数据提示，不是可跨任务硬编码的常数。
  5. 最终结果独立验证：26% 的失败轨迹出现 fabrication，且通常发生在锁死后。完成声明必须由独立测试、artifact diff 或外部 verifier 支撑，不能复用 agent 自己选择的“成功证据”。

6.3 研究品味

这篇工作展示了一个很好的拆题方式：当 outcome 太粗时，不急着做更细的分类，而是先问它是否把多个时间阶段压成了一个标签。$t_{err}\rightarrow t_{lock}\rightarrow t_{obs}$ 让 failure taxonomy、monitoring 和 recovery 第一次共享同一条时间轴。与 Beyond-Resolution-Rates-Coding-Agent-Behavioral-Drivers 的结论合起来看，一篇告诉我们 trajectory 的结构比长度重要，另一篇告诉我们结构里最该盯的是 假设形成、信号响应与恢复锁死。

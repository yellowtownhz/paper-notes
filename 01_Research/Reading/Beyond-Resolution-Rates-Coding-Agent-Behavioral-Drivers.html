2. 关键问题：Resolution rate 掩盖了 coding agent 失败的真正原因和行为模式

Golden Case -- 问题是什么？

matplotlib-23476（Figure 3）：HiDPI 屏幕上 matplotlib 内部把 figure DPI 翻倍来适配 retina 显示，同时在 _original_dpi 里记原始值。bug 在 Figure.__getstate__()（Python pickle 序列化调用的方法）保存了翻倍后的 DPI 而不是原始值，每 pickle/unpickle 一次 DPI 就翻一倍：200 -> 400 -> 800 -> ...

Gold patch 只有 3 行：序列化前把 _dpi 重置为 _original_dpi。人类标注难度 <15 min，单文件、单 hunk。

19 个 agent 全军覆没。最好的 agent 花了 61 步，正确找到了 figure.py，也理解了 DPI 翻倍问题——但它去改了 4 个 backend 文件（backend_macosx.py、backend_agg.py、backend_bases.py、_macosx.m），试图在 display scaling 层面阻止 DPI 翻倍。方向完全反了：agent 和 gold patch 都解决同一个 symptom，但 agent 在 display layer 干预，gold patch 在 serialization layer 干预。Patch 能编译，agent 自己的测试也过了，但 SWE-bench 的 fail-to-pass 测试验证的是 root cause 层面的行为，所以挂了。

这不是个例。12 个 "patch 简单但没人做对" 的任务全是这种模式。

三层问题意识：

第一层：patch complexity 不能预测任务难度。 之前的研究（Multi-SWE-bench、SWE-bench Pro、Ganhotra blog）默认 patch 越大越难。但这 12 个 never-solved task 的 patch 都很简单（单文件、<=10 行），人类标注也认为容易。patch 复杂度在 never-solved 和 always-solved 之间没有统计差异（Mann-Whitney p=0.24, Cliff's delta=0.24）。不过注意，patch complexity 在整体 500 个 task 上确实和难度有一定相关性（rho=-0.380, Related Work section），只是对这些 edge case 失效。

第二层：trajectory length 和 failure 的关联是伪相关。 Majgaonkar et al. (2025) 报告失败 trajectory 比成功的长 12.6-82.5%，但没控制 task difficulty。难的 task 本来就让 agent 跑更多步，而且失败率更高。控制了 task difficulty 后，这个关联完全反转。

第三层：之前的研究把 LLM 能力和 framework 设计混在一起。 Martinez and Franch (2025) 把 agent 当整体比较，但一个 agent = LLM + framework，到底谁在主导？

3. 关键方法：大规模控制实验 -- 9,374 条 trajectory 的 within-task paired comparison

Golden Case -- 方法怎么跑？

还是 matplotlib-23476。分析路径：

  1. 任务分类：先按 resolution rate 把 500 个 task 分三档：never-solved (55)、contested (416)、always-solved (29)。matplotlib-23476 落入 never-solved 且 patch 简单（3 行、1 hunk、1 文件），进入 12 个 edge case 的深度分析。
  2. 定量筛选：拿 12 个 never-solved 和 25 个 always-solved 的 simple-patch task 做 90 个特征的 Mann-Whitney U 检验。patch 复杂度无显著差异，但 fail-to-pass test count 等 5 个特征显著。
  3. 定性分析：检查 top agent 在这 12 个 task 上的 trajectory，对比 submitted patch vs gold patch。10/12 是 architectural reasoning gap。
  4. 配对比较（RQ2）：对同一个 task，对比成功 agent 和失败 agent 的 trajectory 结构。
  5. 因子分解（RQ3）：固定 LLM 换 framework / 固定 framework 换 LLM，看谁影响更大。

核心模块 1: Enriched Trajectory Encoding（13-symbol 编码）

之前的工作要么用 8 种 action type（Bouzenia & Pradel），要么抽象为 4 步（Graphectory）。关键区别是这套编码 jointly encode agent action + environment response——同样是 edit，成功的 edit（P）和触发 SyntaxError 的 edit（Ps）是不同 symbol：

Symbol 含义 来源
P Clean patch edit 后 observation 无报错
Ps Patch + SyntaxError edit 后 observation 含 SyntaxError
Pi Patch + ImportError edit 后 observation 含 ImportError
Pr Re-patch（对已编辑文件再次 edit） edit on previously edited file
Vp Validation pass 测试通过
Vf Validation fail 测试失败
Ve Validation runtime error RuntimeError
Lb Browse 整个文件 view 不带 --view_range
Lt Targeted read view 带 --view_range 或 goto
Ls Search grep、search_dir、search_file
Vr Reproduction script reproduce_*.py 等
E Environment setup pip/apt/conda/build
G General/other submit/cd/pwd/think

编码用 deterministic regex 从 .traj 文件提取，失败率只有 18/9,374 = 0.2%（Table 1）。

核心模块 3: Two-Approach Paired Comparison（Algorithm 1）

方法论上最精彩的设计。为了控制 confound，设计了两种 approach：

Approach A（fix agent, vary tasks）：固定一个 agent，比较它在 resolved vs failed tasks 上的 trajectory。控制了 agent identity，但被 task difficulty confound。用一侧 Mann-Whitney U + Cliff's delta。

Approach B（fix task, vary agents）：固定一个 task，比较成功 vs 失败 agent 的 trajectory。控制了 task difficulty，但被 agent identity confound。对每个 contested task 算 delta(t) = mean(failed) - mean(resolved)，再用 Wilcoxon signed-rank 检验所有 task 上的 delta 分布。

关键逻辑：两个 approach 给出相反结论 = 那个 metric 是 confounded 的。两个 approach 一致 = 那个 behavioral dimension 是 robust 的。

核心模块 4: RQ3 的自然实验

利用 SWE-bench 提交数据天然形成的 LLM x Framework matrix：

  • 固定 framework 换 LLM：隔离 LLM 效应
  • 固定 LLM 换 framework：隔离 framework 效应

除 aggregate resolution rate 外，还用 per-task outcome agreement 做细粒度分析：同 LLM 不同 framework 的 agent pair 在 500 个 task 上有多少给出相同结果。

与已有方法的区别

  1. 规模：9,374 条 trajectory、19 个 agent。之前最大的研究（Bouzenia & Pradel）只有 120 条 trajectory、3 个 agent——规模差 78x
  2. Complete matrix：每个 agent 都跑了全部 500 个 task，可以做 within-task comparison
  3. Enriched encoding：把 environment response 编进去了，之前只编 agent action
  4. Two-approach design：显式揭露 confound，不是忽略它

4. 数据集：SWE-bench Verified 500 tasks x 19 agents = 9,374 trajectories

  • 评估数据: SWE-bench Verified -- 500 个来自 12 个开源 Python 仓库的真实 bug 修复 task
  • Agent 覆盖:
    • 8 个 framework: SWE-agent, OpenHands, Trae, Skywork, CodeSweep, EPAM-AI, SAGE, Sonar
    • 14 个 LLM: 4 个 Claude 变体、3 个 GPT 变体、Kimi-K2、Devstral、Qwen-32B、Doubao 等
    • 19 个 agent（framework x LLM 的组合子集）
  • 数据来源: SWE-bench Verified leaderboard 的公开提交，从 benchmark 作者维护的 public experiment bucket 下载
  • 缺失: 3 个 agent 有轻微缺失（443-499 个 task），由超时或基础设施故障导致
  • 无训练数据：纯分析研究，不训练模型
  • 关键约束: 12.4% 的总计算量花在 55 个 never-solved task 上——零回报的资源浪费

5. 关键结果：Patch complexity 不能预测失败，trajectory structure 才是关键信号，LLM 能力主导 agent 表现

RQ1: 12 个 "简单" task 全军覆没 -- architectural reasoning gap

  • 500 个 task 的 resolution rate 呈双峰分布：55 个 (11%) never-solved，416 个 (83%) contested，29 个 (6%) always-solved（Figure 2）
  • 12 个 never-solved 的 simple-patch task vs 25 个 always-solved 的 simple-patch task：
    • patch 复杂度不可区分：mean total changes 4.75 vs 3.76, p=0.24, Cliff's delta=0.24
    • 5 个显著特征（p<0.05）全是 test-demand 和 issue-description 类（Table 4）：
Feature Never-solved Always-solved Cliff's delta p
Fail-to-pass count 2.42 1.24 +0.61 (L) <0.001
FTP test files 2.17 1.20 +0.55 (L) 0.001
Test patch files 1.58 1.00 +0.33 (M) 0.003
Test patch changes 21.25 12.64 +0.46 (M) 0.025
Has repro code 0.67 0.24 +0.43 (M) 0.014

  • 但限制到 <=5 changes 后，test-demand 差异变不显著——说明定量特征对这些 edge case 的解释力有限

  • 定性分析（Table 5）：12/12 的 best agent 都找到了 gold-patch file，10/12 编辑了它，但 10/12 的失败是 architectural reasoning gap：

Task Gap type

RQ2a: Trajectory length 是 confounded 的伪信号

  • Approach A（fix agent, vary tasks）: 对所有 19 个 agent，failed trajectory 都显著更长（p<0.001），gap 从 +14.0% 到 +111.9%（Table 6 上半部分）。看似确认了 "失败 = 更长"。
  • Approach B（fix task, vary agents）: 结论反转！同一个 task 上，成功 agent 平均走 44.0 步，失败 agent 只走 39.6 步（成功的长 10.0%）。416 个 contested task 中 263 个 (63%) 的 resolved trajectory 更长（p=1.9e-9, Wilcoxon signed-rank）（Table 6 下半部分）。

trajectory length 同时反映 task difficulty（正相关：所有 agent 的 Spearman rho 从 -0.13 到 -0.57, 全 p<0.01, Figure 4）和 agent capability，方向相反。单独用没意义。

RQ2b: Trajectory structure -- 三个 robust 的行为维度

用 Approach B（控制 task difficulty）分析后，三个维度和成功率有稳定相关：

行为维度 Metric rho Direction
Context gathering 第一次 edit 前的 reading 步数 +0.68 (p<0.001) 推迟 edit -> 更高成功率
Opening patch intensity 前 10 步中 patch 比例 -0.78 (p<0.001) 越早 patch -> 越低成功率
Validation effort trajectory 中 validation 步占比 +0.50 (p<0.05) 更多 validation -> 更高成功率

（Figure 6a/b/c）

具体例子：claude-opus-4.5 平均第 9.4 步才开始编辑，claude-3-opus 在第 0 步就开始。Sonar/claude-opus-4.5 花 39.3% 在 validation 上，SWE-agent/gpt-4 只花 13%。

一个 telling example（Figure 5, 之前两个 note 都漏了）：astropy-13579 上，CodeSweep/kimi-k2 和 SWE-agent/gpt-4 都走了 32 步，但 CodeSweep 先探索（4 个 Lb 步），经历 patch-fail 循环后最终通过测试；SWE-agent/gpt-4 第 1 步就开始 patch，陷入 P->Ve spiral 再也没出来。Same length, completely different structure, completely different outcome。

关键发现：这三个维度是 agent-determined、不随 task 调整的（Figure 7）。claude-3-opus 不管 task 多复杂都在第 0 步开始编辑，OpenHands/claude-4-sonnet 不管多简单都等到第 9.5 步。每个 agent 对 patch complexity 的斜率接近零。

Outlier 值得注意：Trae/doubao 达到 78.5% resolution rate 但几乎不做 validation（0.1%），说明足够强的 LLM 可以不靠 test-driven iteration 直接出正确 patch。

RQ3: LLM 能力主导，framework 差异随 LLM 进步缩小

  • 固定 framework 换 LLM：SWE-agent 跨 6 个 LLM resolution rate 跨度 51.5 pp；OpenHands 跨度 31.5 pp（Figure 8）
  • 固定 LLM 换 framework：claude-4-sonnet 跨 framework 只差 3.8 pp，claude-3.5-sonnet 差 19.4 pp
  • Framework gap 随 LLM 进步收窄: 19.4 pp (claude-3.5-sonnet) -> 3.8 pp (claude-4-sonnet) -> 0.9 pp (claude-opus-4.5)

Per-task agreement（Figure 9）:

  • 同 LLM 不同 framework: 71% (claude-3.5-sonnet) -> 85-88% (claude-4-sonnet) -> 93% (claude-opus-4.5)
  • 同 framework 不同 LLM: 47-85% (SWE-agent), 66-88% (OpenHands)——远低于 same-LLM

Prompt 影响随 LLM 增强而减弱（Figure 10）：SWE-agent prompt 350 字符 vs OpenHands prompt 5,602 字符（16x 差距）。OpenHands 规定了 8-phase workflow。然而对 claude-4-sonnet，两个 framework 的 validation work 几乎一样（18.2 vs 20.0 actions/trajectory），resolution rate 只差 4 pp。prompt 改变了 which tools agent 用（SWE-agent 产出更多 reproduction script，OpenHands 更多 search），但没改变 how much work 它做。额外的 prompt 细节还增加了 overhead（60 vs 56 median steps）却没提升结果。

对 claude-3.5-sonnet 则不一样：同样的 framework 切换带来 20 pp 的提升。弱 LLM 确实从丰富 prompt 中获益。

6. Insights

6.1 对论文本身的 Comments

Trajectory length 方向反转是整篇文章的 star finding。 "失败的 trajectory 更长" 在 Approach A 下成立但在 Approach B 下反转——Simpson's paradox 的一个实例。之前的研究（Majgaonkar et al.）看到的 pattern 是假的，聚合数据的方向和控制变量后的方向完全相反。这个发现本身比它的具体结论更有价值——它说明 coding agent 领域的 observational study 如果不控制 task difficulty，什么 trajectory-level 的结论都可能是 confounded 的。

但 RQ2b 的三个 "robust" 相关性有 N=19 fragility。 Figure 6 每个点代表一个 agent，N=19。rho=+0.68 在 N=19 Spearman 检验下刚好在 p<0.001 显著性边界上。移除 1-2 个 outlier（比如 Trae/doubao 的 near-zero validation + 78.5% resolution）可能就让显著性消失了。更关键的是，context-gathering delay 和 resolution rate 的相关可能是个 proxy：delay longer 的 agent 恰好是更新更强的 LLM（claude-opus-4.5 vs claude-3-opus）。correlation 是 across-agent 的，没法区分 "策略本身有效" 和 "更强的模型碰巧用了这个策略"。[?]

Single-run 是最大的方法学弱点，影响所有三个 RQ。

  1. RQ1 的 "never-solved" 分类建立在每个 agent 只跑一次的基础上。如果每个 agent 跑 5 次，有些 task 可能偶尔被解决，"architectural reasoning gap" 的 claim 就得修正。论文引用了 Brown et al. (2024) "Large Language Monkeys" 但自己只有 single run。
  2. RQ2 的配对比较在 single run 下没法估计 within-agent variance。rho=+0.68 这些相关系数是 across-agent 的，无法排除 agent 内部的随机波动。
  3. RQ3 的 per-task agreement（93%）在多次采样下大概率会下降。

12 个 edge case 的定性分析有确认偏差风险。 论文只看了 best agent 的 trajectory 并归因为 "architectural reasoning gap"，但没系统检查其他 17-18 个 agent 是否呈现不同失败模式。完整分析在 supplementary material 里，正文只呈现 best agent 的 trajectory，给人 cherry-picking 的感觉。

"Agents don't adapt strategy to task complexity" 的 claim 只测试了对 patch complexity 的适应性（Figure 7 的 x 轴是 lines changed）。Agent 可能对其他 task 维度（repo 类型、issue 描述质量）有适应性。这个发现被泛化为 "agents apply a fixed strategy regardless of what the task demands" 是过度推断。

Framework gap 缩小的趋势只有 3 个数据点（claude-3.5-sonnet, claude-4-sonnet, claude-opus-4.5），全来自同一个 model family。这个趋势是否能复现到 GPT 系列或开源 LLM 上是个问号。[?]

一个论文没讨论的 confound：LLM 和 inference configuration 是 bundled 的。 不同的 leaderboard 提交可能用了不同的 temperature、top-p、multi-agent pipeline（比如 SAGE 同时用 claude-4.5 和 gpt-5）。"LLM dominates" 的 claim 实际上混合了 model identity 和 full inference configuration。

Validation quality vs quantity 的问题。 论文报告 validation effort（rho=+0.50）但没区分 "跑了多少测试" 和 "跑了正确的测试"。Trae/doubao 的 outlier（78.5% resolution + 0.1% validation）暗示 raw validation volume 不是 mechanism——这说明 validation effort correlation 可能只是一个 proxy for "not being a weak model" 而不是一个 causal strategy。

Architectural reasoning gap 是否可通过 scaling 解决？ 论文在 Implications 中暗示 scaling 不够，可能需要显式的 codebase structure representation（call graph、dependency graph）。这个判断目前证据不足——可能下一代 LLM 的推理能力就能解决这类问题。[?]

6.2 对未来的预测

LLM 继续进步的话 framework engineering 的边际价值会越来越低。19.4 pp -> 3.8 pp -> 0.9 pp 的趋势（虽然只有 3 个数据点）方向很清楚。SWE-agent 的 350 字符 prompt 在强 LLM 上已经和 OpenHands 的 5,602 字符 prompt 一样好。但这个 "framework 不再重要" 有一个 escape clause：如果 framework 开始提供新的观察能力（codebase graph analysis、architectural dependency checker），而不是仅仅做 prompt engineering，那 framework 可能重新变得重要。论文的数据暗示 framework 的真正价值不在 prompt 设计，而在于能否给 LLM 额外的 perception。

6.3 研究品味

Two-approach design 本身是一个通用的方法论工具。很多 empirical study 用一种比较方式就下结论，不考虑 confound。这里把 Approach A 和 Approach B 对比着做，用 reversal 来证明 confound 的存在——"设计实验让 confound 可见" 比 "假装 confound 不存在" 高级得多。在做任何涉及多因素交互的 observational study 时都值得问：如果我从另一个方向切数据，结论会反转吗？

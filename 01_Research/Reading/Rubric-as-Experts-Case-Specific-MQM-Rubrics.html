论文笔记: Rubric-as-Experts: Case-Specific MQM Rubrics for Translation Quality Evaluation

1. 背景信息

  • 作者/团队: Weilu Xu, Yunzhi Shen, Xinye Wang, Ranfei Dang, Shujian Huang（通讯）——南京大学，软件新技术国家重点实验室
  • 发表: arXiv:2606.21559v1 [cs.CL]，2026-06-19（预印本，无 venue，看着像投稿版）
  • 任务: span 级翻译质量评估（QE）——不是给译文打个总分，而是在译文里精确框出错误片段，用 MQM 错误分类体系引导 LLM
  • 一句话: 别再给所有译文套同一套 MQM rubric。用一个轻量 router 按每条 case 的难度，动态决定"给 LLM 评审员看多大的错误类型搜索空间"。

2. 关键问题：MQM rubric 空间该多大，应该 case-by-case 定，而不是全局固定

Golden Case — 问题是什么？ 论文 Table 5 一条 Zh-En 样本最能说明问题。同一条机器译文（里面把"中西方"误译成了 "Midwest"），只是把喂给同一个 LLM 评审员的 rubric（错误类型清单）换大换小，结果差异巨大：

Rubric 大小 Precision Recall F1
Baseline（无细粒度 rubric） 1.000 0.111 0.200
Small Rubric 1.000 0.222 0.364
Medium Rubric 0.875 0.778 0.824
Full Rubric 0.310 1.000 0.474

Rubric 越大，评审员探索得越广（recall 从 0.11 一路涨到 1.0），但也越容易乱标（precision 从 1.0 崩到 0.31）。这条 case 的最优点在 Medium——不是最小也不是最大。

⚠️ 但要清醒：这是单条手挑样本，medium 恰好赢。它证明的是"存在 case-level 最优粒度"这个现象，不是"框架能把每条都路由对"。对照后面主表 Full Dynamic 的 F1 只有 33.78，离这里 medium 的 0.824 差得远——所以"每条选对粒度"这件事，框架实际上远没做到。

核心 framing：rubric 不只是"打分标准"，它其实是 LLM 的搜索空间 / 探索边界。MQM 子类型给得越多，模型越倾向从多个语义角度审视译文，recall 涨但 false positive 也涨；给得越少，precision 高但漏检多。这是个此消彼长的 tradeoff，不是单调改进。

  • 动机 / 为什么重要: span 级 QE 要的是"精确定位错误片段"。LLM 在翻译生成上很强，但在 span 级错误定位上，老牌系统 CometKiwi 之类仍有竞争力——说明 LLM 这块能力没被释放出来。作者的判断：瓶颈不全在模型能力，而在评估搜索空间怎么暴露给模型。
  • 之前的方法卡在哪（两条路都是"静态"的）:
    • Free-form rubric 生成（LLM 自己现编标准）：灵活，但 coverage 不稳定、粒度不一致、行为不可控。
    • 固定 MQM rubric prompting（GEMBA-MQM, RUBRIC-MQM）：一致性好，但一套 rubric 套所有 case，对异质样本适配差。
    • 缺一个"在预定义 MQM 结构内做 case-specific 动态分配"的中间态。
  • 为什么是 span 级 QE 特有的难点: 翻译质量有多种可接受解释，"可接受变体"和"真错误"边界模糊。模型不仅要检错，还要控制严格度和探索范围。search-space mismatch 本身就是影响 QE 的独立因子。

3. 关键方法：级联 router（correctness gate → major-category router → compact → expansion gate → budget router）按 case 从 MQM 树里选搜索空间大小，再喂给 LLM 评审员

Golden Case — 方法怎么跑？ 继续上面那条 "Midwest" 译文，走一遍完整 pipeline：

  1. Correctness gate（"这条要不要直接放过？"）：先判是不是根本没错。这条明显有错，p_ok 低于阈值，不放过。
  2. Major-category router（"该看哪几个 MQM 大类？"）：多标签预测相关大类，主要是 Accuracy（误译/漏译），可能带一点 Style。最多激活 3 个大类。
  3. Compact 评估：用选中大类下少量最相关 subtype（如 Mistranslation, Omission）先跑一遍，抓到核心的 "Midwest" 误译。
  4. Expansion gate（"compact 够不够？"）：看 compact 结果 + hidden state。这条错误多、句子长，p_exp 高，需要扩。
  5. Budget router（"扩到 medium 还是 full？"）：理想路由到 medium（Table 5 里 F1=0.824 的甜点），而不是 full（会掉到 0.474）。
  6. Span detection：把选定粒度的 subtype 描述拼进 prompt，评审员 f_eval 输出 span，最后合并重叠 / 去重 / 过滤非法 span。

一句话：router 负责"给多大搜索空间"，LLM 评审员负责"在空间里找错"。router 很轻（LoRA + 线性头），重活还是 LLM 干。

3.1 整体架构（级联 gating，Figure 2）

数据流（按 §3.1 + Figure 2）：(x, y) → correctness gate（廉价早退）→（不放过）→ major-category router → compact eval → expansion gate →（需扩）→ budget router(medium/full) → 组装 rubric → f_eval span 检测 → 后处理。

⚠️ 论文自相矛盾的一处：§3.1 和 Figure 2 caption 明确说 "the framework first applies a correctness gate"（correctness gate 最前置）；但 §3.3 "Two-stage MQM Routing" 和 Appendix B.2 的叙述顺序是先讲 major-category router、再讲 correctness gate。本笔记按架构图（correctness gate 优先）叙述——这是论文本身的描述 bug，复现时以 Figure 2 为准。

3.2 结构化 MQM rubric 空间

  • 用 MQM taxonomy 构造 rubric 池 R_MQM，每个 subtype 配一句自然语言描述，作为原子 rubric 单元。case-specific rubric 就是从池里选子集：

    公式 (2): R(x,y) ⊆ R_MQM（R_MQM = 完整 MQM 派生池；R(x,y) = 这条 case 挑出的子集）

  • 7 个 MQM 大类作为顶层路由空间（Appendix A, Table 6）：Accuracy（Mistranslation; Number; Date/time; Overtranslation; Omission）、Audience appropriateness、Design and markup、Linguistic conventions（Grammar; Agreement; Word order; Punctuation; Spelling）、Locale conventions、Style、Terminology。

  • 关键设计：下层节点全部 flatten 成 subtype 候选，每个带原始 MQM 描述。既保留层级语义，又简化推理接口。

  • 与 free-form 的本质区别：不发明新标准，只从预定义 MQM 空间选子集，保住 MQM 可解释性。

3.3 路由模块与公式

先用一句大白话给每个 gate 定位，再上公式：

(a) Major-category router（"该看哪几个大类"，多标签分类）

  • 取 Qwen3 末层、最后一个非 padding token 的 hidden state 作句表征： 公式 (8): h(x,y) = H^(L)_{ℓ_i}，ℓ_i = Σ_t m_{i,t} − 1（m = attention mask）
  • 多标签头：公式 (9) z_c = w_c^T h + b_c，p_c = σ(z_c)，c ∈ 7 大类
  • 训练损失（软标签加权 BCE，公式 10）: L_cat = −Σ_{c∈C'} [ ω_c q_c log p_c + (1−q_c) log(1−p_c) ]
    • q_c ∈ {0, 0.5, 1} 是软监督，由 word-level span overlap 推出（强重叠 1、部分 0.5、否则 0）
    • ω_c 正类重加权缓解类别不均衡；全零（无错）样本额外下采样
  • 推理是 recall-oriented（公式 11-12）: 留最高分大类 c_1，其余满足 p_c ≥ τ_cat 或 p_c ≥ p_{c1} − δ 则一起激活，最多 3 个；极低置信 fallback 到 Accuracy。宁可多召别漏。

(b) Correctness gate（"要不要直接放过"）

  • 公式 (4/13-14): p_ok = σ(w_ok^T h + b_ok)，p_ok ≥ τ_ok → 判无错、提前终止
  • Section 5.1 叫它 "no-error gate"，故意 recall-preserving——~95% 真有错 case 会被放行下去

(c) Expansion gate（"compact 够不够"）

  • 公式 (5/15-16): p_exp = σ(w_exp^T [h; e_3(x,y)] + b_exp)
  • e_3(x,y) = compact 评估后提取的特征——关键决策点：expansion 决策用到了 compact 的实际输出，不是纯凭输入猜。p_exp < τ_exp 保留 compact，否则进 budget router。（原文 eq5 写 e(x,y)、eq15 写 e_3(x,y)，指同一物。）

(d) Budget router（"扩到 medium 还是 full"）

  • 公式 (17-18): b̂ = argmax_{b∈{medium,full}} π_b(x,y,e_3)。medium = 更广但仍选择性；full = 激活选中大类下所有 subtype。

3.4 路由监督：utility-based oracle（复现核心）

router 的监督标签靠一个 oracle 定义，对每条训练样本实际跑三种粒度、算 F1，挑效用最高的当金标准：

  • 效用函数（公式 19）: U(g) = F1(g) − λ · cost(g)，其中 F1(g) 是用 gold label 算的 word-level F1
  • oracle 粒度（公式 20）: g* = argmax_{g∈{small,medium,full}} U(g)
  • 各 gate 监督：correctness gate L_ok = BCE(a_ok, y_ok)（21）；expansion gate 标签 y_exp = I[g*≠small]（22），L_exp（23）；budget router 只在需扩样本上训 L_bud = I[g*≠small]·CE(π, index_B(g*))（24）；总损失（25） L = L_cat + L_ok + L_exp + L_bud

复现要点 & 缺口: (1) oracle 标签要对每条 dev 样本用 LLM 跑 3 次（small/medium/full）拿 F1，是训练前的一次性离线成本，强依赖 dev 有 gold span。(2) λ 和 cost(g) 全篇没给值/定义 [?]——而它俩直接决定 oracle 标签、进而决定整个 router 学什么，这是可复现性最大的黑洞。(3) 所有阈值 τ_cat, δ, τ_ok, τ_exp 也都没给数值，也没说是否在 dev 上 grid search [?]。

3.5 动态 span 检测（推理端）

  • 从池里检索选中大类下的 subtype 描述：公式 (26) R̂(x,y) = Top-k̂ ({r ∈ R_MQM : Major(r) ∈ Ĉ(x,y)})
  • 组装进 prompt，评审员输出 span：公式 (27/7) Ŝ = f_eval(x, y, R̂(x,y))。评审员被指示只输出从译文逐字复制的 span。
  • 后处理（Appendix B.4）: 高重叠 span 合并 / 去重 / 过滤译文里不存在的非法 span / 可选地把 think 与 no-think 输出做 calibration 合并（⚠️ 这一步本身是隐藏的 self-ensemble，见 §6.1）。

3.6 训练与推理配置（复现必需）

  • Backbone: Qwen3-4B / Qwen3-8B，thinking mode，vLLM，RTX A6000。thinking prompt 额外 prime 一个 <think>Okay, 前缀。
  • Major-category router: frozen Qwen3-8B + 线性多标签头 + LoRA r=4, α=8, dropout=0.05，训 3 epochs
  • Rubric-granularity router: LoRA r=8, α=16, dropout=0.05，训 6 epochs；两个 router 都 bf16
  • Span 评估解码: 确定性，temperature=0.0, top_p=1.0；vLLM max gen 3072，max len 8192，GPU mem util 0.90，batch 8/GPU
  • Prompt 缺口 [?]: Appendix A.2–A.5 只列了 prompt 的名字/用途（Baseline span prompt、Hierarchy merge: major-subtree detection prompt、Top-k-best minimal-span subtree prompt、Subtype-ranking prompt 等），正文没贴任何一个 prompt 的实际文本。对一篇核心贡献是 rubric/prompt 设计的论文，prompt 全缺失是硬伤，需看代码。

4. 数据集：WMT23 span 级 QE，Zh-En + En-De；dev 训 router、test 评估

  • 训练数据: WMT23 span-level QE development set 训 router（含 oracle 粒度标签构造，需 gold span）。有错/无错不均衡，靠全零样本下采样处理。
  • 评估数据: WMT23 span-level QE test set，两个语向 Zh-En 和 En-De（Blain et al. 2023）。
  • 指标: word-level Precision / Recall / F1 / MCC，预测 span 转 word-level 标签与 gold 比对。MQM subtype 只用于 rubric 构造/prompting，不作为直接评估目标。

⚠️ 数据规模天花板很低：只有 WMT23、只有 2 个语向、train/test 同分布。Limitations 自己承认跨标准、跨语言、unseen dataset 的鲁棒性 "insufficiently explored"。所有"动态优于静态"的结论都绑死在这一个 benchmark 上，无 seed / std / 置信区间。

5. 关键结果：两语向两规模上 MCC 都涨，但涨幅几乎全来自 recall 暴涨，且跨规模行为不一致

Method Zh-En P R F1 MCC En-De P R F1 MCC
CometKiwi – – – 26.90 – – – 21.50
DCSQE – – 28.61 28.12 – – 30.61 27.11
GEMBA – – 16.11 18.21 – – 13.21 18.17
Qwen3-4B 17.04 45.79 24.84 19.70 16.31 16.19 16.25 10.23
Qwen3-8B 18.22 53.55 27.18 23.36 19.16 23.43 21.08 14.76
Qwen3-14B 21.94 44.78 29.45 24.52 23.99 20.83 22.30 17.16
Ours-4B 19.71 69.51 30.71 29.25 31.75 31.40 31.57 26.60
Ours-8B 22.29 69.80 33.78 32.40 22.68 60.16 32.94 29.57
  • Zh-En：Ours-8B 最好，F1 33.78 / MCC 32.40，比 DCSQE 高 +5.17 F1 / +4.28 MCC，比同规模 Qwen3-8B MCC 高 +9.04（Ours-4B +9.55）。
  • En-De：Ours-8B F1 32.94 / MCC 29.57，比 DCSQE 高 +2.33 F1 / +2.46 MCC。

审稿人最强攻击点（每条 2–3 句，证据侧）：

  1. 涨幅几乎全靠 recall 换来的。Zh-En Ours-8B recall 69.80 vs Qwen3-8B 53.55，precision 只有 22.29（相对 baseline 18.22 涨得有限）。对要"给译员/系统指出错误"的 QE 场景，22% precision 意味着 4/5 标错，实用性存疑。这更像"把阈值调松、多标 span"，而非"评估更准"。

  2. 跨规模 P/R 行为翻转，像调参 artifact。先看现象：En-De 上 Ours-4B 是 P 31.75 / R 31.40（平衡），Ours-8B 却是 P 22.68 / R 60.16（recall 翻倍、precision 掉）——同一框架在同一语向上，4B 和 8B 呈现相反的 P/R 取舍。再看推断：Table 9 里 Ours-8B En-De 从 "+Expansion Gate" R=30.10 突跳到 "Full Dynamic" R=60.16，这个 2 倍跳变只由 budget router 造成、且只在 8B En-De 出现，强烈提示阈值/预算被 per-setting tune 过。

  3. Correctness gate 单独加是负收益（Table 2, Zh-En 8B）：Compact MCC 21.48 → +Correct Gate 20.74（降了）。真正起作用的是 Expansion Gate（28.88）。论文以"级联三段式都有用"叙述，但证据显示 correctness gate 本身拖后腿。

  4. No-error gate 准确率低于多数类基线（Table 4）：Zh-En 准确率 52.22%，但样本 G-OK=1109 / G-Bad=555 共 1664，全预测 OK 的多数类基线就有 66.6%——gate 比闭眼猜还差 14 分。En-De 64.88% 也只比多数类 59.9% 高一点。论文用"recall-preserving，保留 95% 错误样本"解释，但那本质等于"这个 gate 几乎不过滤、约等于没用"。把一个准确率低于 baseline 的模块包装成设计特性，需要 push。

  5. 缺 same-backbone static rubric 对照。§4.2 原文其实描述了 Direct prediction 和 Static MQM rubric 两个 baseline，但 Table 1 只有 vanilla Qwen（=direct prediction），没有 same-backbone 的 static MQM rubric 行——论文声称有、主表里却缺席。它只以 Fixed Compact/Comprehensive 出现在 ablation。加上 CometKiwi/DCSQE/GEMBA 数值 "taken from prior work" 未必对齐（GPT-4 的 GEMBA 只有 16.11 F1，低得可疑），主表缺一个公平的强对照。

  6. 两个核心路由组件的 test 端准确率从未报告（已核全文，确无该表）。论文报了 major-category coverage（Table 3）和 no-error gate accuracy（Table 4），但没有任何数字告诉你 expansion gate / budget router 在 test 上路由对了没有。复杂度分析（§5.2）用的全是 oracle g*。也就是说：核心贡献（动态选粒度）的组件本身零直接评估，只能靠端到端 MCC 反推。

消融（Table 2，Zh-En Qwen3-8B）

Setting P R F1 MCC
Compact（固定小） 14.80 65.63 24.16 21.48
Comprehensive（固定全） 10.89 76.50 19.07 16.80
+ Correct Gate 13.70 70.45 22.95 20.74
+ Expansion Gate 18.93 71.79 29.96 28.88
Full Dynamic 22.29 69.80 33.78 32.40
  • 核心 tradeoff 定性扎实、不 challenge：固定 Comprehensive recall 最高（76.50）但 precision 最低（10.89）、MCC 垫底；Compact 保 precision 但漏复杂错误。Full Dynamic 在两语向两规模都拿最高 MCC。

Router 可靠性分析（§5.1）

  • Major-category coverage（Table 3，累积 recall）: Zh-En ≤1 大类覆盖 87%、≤2 达 97%、≤3 达 99%；En-De 更分散，≤1 覆盖 69%、≤2 81%、≤3 95%。→ 系统最多用 3 个大类，兼顾高 recall 与避免全空间噪声。
  • No-error gate（Table 4）: 准确率 Zh-En 52.2% / En-De 64.88%，故意偏向保留可疑 case（~95% 真错样本被保留），false-positive 不直接丢、交给下游 rubric 评审约束。（低于多数类基线的解读见上方攻击点 4。）

动态复杂度分析（§5.2，Figure 3/4）

  • 相关性明确：错误 span 越多 / 源句越长 → 需要 Comprehensive 的比例稳步上升，Compact 失效，Expanded 是中等复杂度的过渡带。Appendix D 在 4B 和 En-De 上复现了同一趋势。
  • ⚠️ 可能的循环论证 [?]：B 版指出所谓"所需粒度"若就是 oracle g*（用 gold F1 事后算出），则"复杂样本需要更宽 rubric"和"router 学会分配"是用同一 oracle 定义推出的，不是独立验证。核对全文：原文用词是 "required rubric granularity"，没明说 Fig 3/4 分层用的是 oracle 标签还是 test 端 router 预测。若是 oracle，则循环论证成立；若是 router 预测，则不成立——原文未坐实，保留为条件式质疑。

Rubric = 推理约束，不只是标签清单（Appendix E，最有价值的机制 claim）

  • 自然假设：既然模型 free-form 时会同时输出 span 和其 subtype，那只保留"被预测到的 subtype"应能压缩 rubric 而不丢 span。实测相反：Zh-En Qwen3-8B 上，只留预测到的 subtype，word-level recall 从 ~0.70 掉到 0.46。
  • 解释：R → reasoning paths → Ŝ（公式 30）。更大的 rubric 空间会激活多条部分重叠的推理轨迹（adequacy / fluency / terminology / style / 结构对齐），即使某 subtype 最终没被选中，它出现在 rubric 里也能触发有用的中间推理、暴露额外候选 span。窄空间会让评审员过早收敛。
  • → 动态路由的目的不是"最小化 rubric"，而是"给每条 case 一个足够有表达力的空间"。（⚠️ 但这个 claim 同样只有单个 0.70→0.46 数字支撑，无多设置验证。）

6. Insights

6.1 对论文的 Comments

  • 最反直觉、也最该记的是 Appendix E 的 framing：rubric 不是最终打标签用的 label set，而是塑造评审员推理探索轨迹的 search-space controller。"只保留预测到的 subtype，recall 从 0.70 掉到 0.46"这个实验设计得聪明——它排除了"是不是 subtype 预测错了"这个 confound，直接证明是搜索空间本身在改变解码行为，而非标签匹配问题。如果让我做，我大概率会默认"只留预测子类型 = 无损压缩"，正是被这个实验证伪的直觉。这个视角比方法本身更值得记。

  • 最有价值的独立批判：后处理 + compute 不对等的双重 confound。Ours 相对 vanilla Qwen3 的提升，有多少来自"case-specific 分配"、多少来自这套 ensemble-ish pipeline？两个具体来源：(1) compute 不对等——整条 pipeline 对每条难 case 要跑 LLM 多次（compact → 可能 medium/full 重跑 → think+no-think 双路 calibration），单样本推理成本可能是 vanilla 单次 forward 的 2–4 倍。所以"Ours-4B 打赢 Qwen3-14B 单次"很可能是拿更多 test-time compute 换来的，不是"小模型顶大模型"。(2) think+no-think calibration 是隐藏的 self-ensemble，本身就能涨 recall，和"动态路由"完全正交，却被埋在后处理里从没单独消融。论文缺一个 compute-matched / 固定 medium rubric + 同后处理 的对照来 isolate 掉这两项——很可能相当一部分增益来自它们而非动态路由本身。

  • no-error gate 低于多数类基线（52.22% < 66.6%，Zh-En）：比闭眼猜还差 14 分。作者用"故意 recall-preserving，保留 95% 有错样本"justify，逻辑上说得通，但结合 Table 2 里 +Correct Gate 让 MCC 从 21.48 掉到 20.74，两个事实合起来说明：这个 gate 只负责"别误伤真错样本"（安全垫），既不是精准分流、也不是性能来源。把它包装成设计特性偏粉饰。

  • 复现黑洞：U(g)=F1(g)−λ·cost(g) 里 λ 和 cost(g) 完全没给值/定义，而它直接决定 oracle 标签→整个 router 学什么；各阈值 τ_cat, δ, τ_ok, τ_exp 也无值、无调参说明；prompt 文本全缺失（只有名字）；budget router 的 π_b 用啥结构（又一个 LoRA 头？和 expansion gate 共享 backbone？）也没交代。这些叠加，论文基本不可复现。

  • 跨规模是 artifact 的强信号：En-De 上 Ours-4B（P31.75/R31.40 平衡）与 Ours-8B（P22.68/R60.16 recall 主导）呈相反 P/R 风格，加上 8B En-De recall 从 30→60 的 budget-router 单点跳变——如果 routing 学到的是稳健规律，不该这样，更像 per-setting 调阈值的产物。（其余批判详见 §5，不在此复述。）

6.2 对未来的预测

  • 论文 Limitations 自己点了 exploration-aware decoding——不只在 prompt 层面调 rubric，而是显式建模评审员的探索过程。如果 Appendix E 的"rubric 影响解码轨迹"成立，那把这个约束下沉到 decoding（约束/引导 beam）应该比在 prompt 里塞 subtype 更直接有效。
  • "rubric/prompt 作为 search-space controller"这个 framing 若成立，会外溢到其它结构化 LLM-as-judge（代码评审、RAG 忠实度、多维写作评分）——不是"写更好的 rubric"，而是"按样本控制暴露多宽的评估维度"。但前提是有人先在更大、更多样的 benchmark 上把"动态 vs 静态最优粒度"和"后处理/compute 增益"干净拆开，否则这方向容易停在"看起来涨点但说不清为什么"。

6.3 研究品味

  • 值得学的叙事闭环：先做诊断性实验（rubric 宽窄 → P/R tradeoff，Table 5 + Appendix E）建立 motivation，再上方法，最后用机制分析（0.70→0.46）反过来解释"为什么方法有效"。即便本文方法侧证据偏弱，它的现象侧观察（rubric 影响 decoding 探索）是能立住、可被后续工作复用的。Table 5 单 case 扫粒度（Baseline/Small/Medium/Full 的 P/R/F1 单调变化）是把抽象 tradeoff 讲清楚的最经济手段——一张表顶一段论证（但别忘了它是 cherry-pick）。
  • 反面教材：oracle 信号复用。g*（用 gold F1 算）既用来训 router、又用来做"复杂度需要宽 rubric"的分析，形成循环论证。做这类"自适应分配"研究时，用于验证 motivation 的信号必须独立于用于训练/定义 oracle 的信号，否则分析部分证明不了额外的东西。更进一步的教训：核心组件（expansion/budget router）在 test 上到底路由对了没，必须有直接评估，而不是只报端到端 MCC。

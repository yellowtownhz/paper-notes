Beyond the Black Box: Interpretability of Agentic AI Tool Use

Hariom Tatsat, Ariye Shater

Mechanistic_Interpretability Agentic_Tool_Use Sparse_Autoencoders Activation_Probing

论文笔记: Beyond the Black Box: Interpretability of Agentic AI Tool Use

一句话判断

这篇论文把 agent observability 的窗口从“工具执行后的日志”前移到 动作尚未发生的 decision boundary：读取模型最后 32 个 token 的多层 residual activations，预测此刻是否需要调用工具，以及下一动作属于哪档风险。最可信的结果是 Tool-Need 能提前发现约 75.5% 的漏调；SAE 的价值则不是预测更准，而是把 dense probe 的告警换成可定位、可命名、可消融的 sparse evidence。最大的边界也在这里：消融只改变了 probe，论文没有证明这些 features 因果控制 agent 的真实动作。

1. 背景信息

  • Hariom Tatsat、Ariye Shater，Barclays Quantitative Analytics；arXiv:2605.06890v4，2026 年。
  • 模型：GPT-OSS 20B 与 Gemma 3 27B IT。
  • 训练数据：NVIDIA Nemotron function-calling 多步轨迹；跨分布测试：BFCL 的 limited zero-shot slice。
  • 范围很窄也很清楚：论文不解释 agent 的全部 planning、memory 或长程 reasoning，只监控“下一步回答还是调工具”的瞬间。

Figure 1 应该看哪里？ Memory 和 planning 被淡化，实验真正覆盖的是右侧 tools-and-action 路径。后文所有结论都不能外推成“解释了 agent 的整体决策过程”。

2. 关键问题：日志告诉你做错了什么，但已经太晚

长轨迹里的工具错误有三种典型形态：该调却没调、不该调却调了、调用了高后果工具。它们一旦执行，不只造成单步错误，还会把错误 observation 写回上下文，改变后续整条 trajectory。

传统日志只能看到 Actual；论文增加了另外两条线：

  • Expected：gold trajectory 认为这一步是否需要工具；
  • Internal：动作前激活中的 Tool-Need / Tool-Risk 信号；
  • Actual：runtime 最终是否调用、调用什么。

只有三者放在一起，才能区分“模型内部没意识到需要工具”和“内部已经意识到、但生成动作仍漏掉”这两类完全不同的失败。

Golden Case — Tesla 查询为什么在相邻两步翻转？

Nemotron trajectory 3344 的 step 14 要查询 Tesla income statement，Tool-Need 为 0.881，风险分布为 (low 0.997, medium 0.003, high 0.000)；紧接着 step 15 仍在 Tesla 话题中，但只是已有结果上的 follow-up，Tool-Need 降到 0.202，风险变为 (0.438, 0.484, 0.078)（Table 6；Appendix Table 20）。

两步主题几乎相同，真正变化的是“是否还需要 fresh retrieval”。如果 probe 只认金融词或 Tesla，它不应产生这种翻转。这个例子因此很适合建立直觉，但作者明确称它为 illustrative、non-evaluative trace：表里没有逐步 gold、actual action 和对错列，不能拿它代替正式准确率证据。

3. 关键方法：在每次行动前截断轨迹，读出两级内部信号

3.1 同一条 step 14 → 15 如何穿过监控管线

  1. 把 trajectory 按 depth 排序，为当前 step 重建此前全部 transcript；当前输出和未来步骤不能进入输入。
  2. 在若干层读取 pre-action residual states，对最后 32 个 tokens 做 mean pooling。
  3. 用每层对应的公开 SAE 编码 pooled vector，再把多层 sparse features 拼接。
  4. Tool-Need logistic probe 判断“此刻是否需要工具”；若是 tool row，Tool-Risk softmax 再判断 low / medium / high。
  5. 将 Internal 与 Expected、Actual 对照，理论上可映射到 allow、review、sandbox 或 approval。注意：Figure 2 的处置策略只是概念设计，论文没有测部署阈值、误报成本或拦截收益。

Figure 2 应该看哪里？ 真正完成实验验证的是 pre-action activation → SAE → probes；右侧 feature family 名称及 allow/review/block 策略部分是 illustrative，并不是已上线的 control policy。

3.2 表征与 probe

对层 $\ell$ 的 pooled activation $\tilde h^{(\ell)}$，SAE 编码为：

$$ z^{(\ell)}=\phi\!\left(W_{enc}^{(\ell)}\tilde h^{(\ell)}+b_{enc}^{(\ell)}\right), \qquad z=[z^{(\ell_1)};\ldots;z^{(\ell_m)}]. $$

Tool-Need 是二元 logistic readout：

$$ p(y=1\mid z)=\sigma(w^\top z+b), $$

Tool-Risk 则在 tool-call rows 上训练三分类 softmax。二者不是并列的两个安全结论：Tool-Need 判断“要不要 delegate”，Tool-Risk 只在准备调用后判断启发式风险档。

Backbone / target 监控层 feature 预算 正则
GPT-OSS Tool-Need L3/7/11/15/19/23 post-residual 200 lasso
Gemma Tool-Need L16/31/40/53 post-block residual 2,000 elastic net
两模型 Tool-Risk 同上 各 1,000 elastic net

原文没有交代最终正则强度、elastic-net mixing ratio、seed、分类阈值，以及 SAE checkpoint、latent width、非线性和重构质量。对一项强调可复现监控的工作，这是明显缺口。

3.3 Risk 标签实际测量什么

Tool-Risk 不是由事故或人工安全判断得到，而是按工具名关键词分层（Appendix Table 18）：

  • Low：920 个 read-only retrieval / lookup / finance-data tools；
  • Medium：27 个有界 write/create tools；
  • High：21 个 authentication、外发通信或危险执行 tools。

这些是 distinct tool 数，不是样本数。风险显然还取决于 arguments、权限、环境状态和用户策略：send_email 发草稿给自己与外传客户数据不能只靠工具名归为同一个风险。因此 Probe 2 更准确的名字是 heuristic risk screen，不是已验证的安全风险模型。

3.4 Feature ablation 到底因果了什么

作者把 top-ranked SAE coordinates $z_j$ 置零，再运行同一个 probe。如果概率显著变化或标签翻转，可以说明：

probe 的 readout 功能性地依赖这些 sparse coordinates。

但实验没有把 ablated features 解码回 residual stream，也没有重新生成 agent action。因此它不能说明“这些 features 控制模型是否调用工具”。这一区分是读这篇论文最容易滑过去的地方。

4. 关键证据：先证明信号可读，再问可检查性值不值成本

4.1 Held-out Nemotron：RAW 明显更准

Appendix Table 13 给出同分布汇总（RAW / SAE）：

Metric GPT-OSS 20B Gemma 3 27B IT
Tool-Need accuracy 81.8% / 75.3% 81.0% / 71.4%
Tool-Need macro-F1 0.817 / 0.753 0.810 / 0.714
Tool-Risk accuracy 94.0% / 90.3% 96.3% / 88.5%
Tool-Risk macro-F1 0.799 / 0.699 0.855 / 0.668

所以结论不是“SAE 提升了工具决策预测”，而是：dense residual 中有更强的线性可读信号；SAE 用一部分预测力交换 layer、feature index、自然语言标签和 ablation target。

这项交换是否划算，论文其实还没测：没有 feature-label fidelity、人工审计速度/准确率、额外 latency 或告警处置收益。SAE 在这里提供的是 inspectability affordance，不是已经证实的 audit utility。

顺带一提，v4 的 Table 3 把 Risk macro-F1 写成 GPT/Gemma 的 0.64/0.62，但 Table 5 confusion matrices 和 Appendix Table 13 对应 0.699/0.668。本文按可复算且在附录重复的后者记录，前者应标作表格口径错误 [?]。

4.2 Layer localization 与 probe ablation

  • GPT-OSS 的 top-20 Tool-Need features 有 13 个在 L23；Gemma 主要集中在 L40/L53（Table 7）。这支持 signal 在动作承诺前的后层更集中，但只在作者选定的少数监控层之间成立。
  • GPT-OSS 删除 top-10 features，在 10 个样本中造成 4 次 probe flip，平均 $|\Delta p_{tool}|=0.431$；Gemma 删除 top-200 才有 1 次 flip，平均变化 0.146（Table 10）。这说明两个 probe 的稀疏程度不同，不说明 GPT 的真实 agent policy 更受这些 features 控制。
  • 自动 feature labels 确实能找到 numerical/formal-language 与 credential/authentication 概念（Tables 8–9），但没有人工 fidelity 评估。把“password feature”当作经过验证的机制名称仍然太早。

4.3 Runtime replay：最有用的结果是 omission auditing

GPT-OSS 在 760 个 held-out Nemotron episodes 上（Table 11）：

Step accuracy Missed-tool rate Unnecessary-call rate Tool naming accuracy 漏调被 probe 标记
78.6% 34.2% 7.7% 90.8% 约 75.5%（258/343）

一旦模型决定调用，tool naming 已有 90.8%；真正的瓶颈是“是否 delegate”。而 probe 能在执行前标记约四分之三的 missed calls，这比离线分类分数更直接地支持论文的实际价值：Tool-Need 可以成为高价值 decision points 上的 omission auditor。

4.4 BFCL：有迁移信号，也有严重校准问题

probes 只在 Nemotron 训练，BFCL 不做 retraining、calibration 或 threshold tuning（Table 12）：

Metric GPT-OSS Gemma
Probe 与 gold Tool-Need agreement 87.7% [?] 77.7%
runtime missed-tool rate 10.8% 0.2%
runtime unnecessary-call rate 56.3% 98.5%
episode success 49.2% 50.0%

Gemma 的 0.2% missed rate 不是完美 delegation，而是接近“总是调用”：在 no-tool steps 上 98.5% 都多调。这个结果说明新分布上的 threshold 与 tool prior 至少和 representation 一样重要。

RAW / SAE 在 BFCL 也没有统一胜负：GPT Tool-Need 是 84.7% / 87.6%，Gemma 是 81.9% / 77.7%；Risk 则 RAW 在两个模型都更高（Appendix Table 14）。有限 slice 只能说明两种表征都保留部分 transferable signal，不能给出普适排名。

5. 证据边界：我会在复现前先补什么

  1. 先确认 trajectory-level split。 原文没有报告 train/validation/test 的 trajectory 数和切分单位。相邻 step 共享几乎全部累计上下文；如果按 row 随机切分，会产生严重近重复。这里是潜在风险，不应写成已经泄漏。
  2. 做同样本 RAW–SAE paired comparison。 附录的 RAW/SAE 行数并不完全一致；当前差异同时混有 representation 与可用样本变化。
  3. 把 risk 改成条件函数。 至少使用 tool × arguments × permissions × environment state，并报告每档 support、calibration 和真实处置成本。
  4. 做 generation-time intervention。 修改 feature 后重新生成 tool/no-tool、tool name 与 arguments，才能从“probe explanation”推进到“agent mechanism”。
  5. 真正测审计效用。 让人类在相同告警上分别看到 raw score 与 SAE evidence，比较诊断时间、正确率、误报接受率和 runtime overhead。

6. Insights

6.1 Decision boundary 是这篇论文最有研究品味的选择

观察：它没有尝试一次解释完整 agent，而是只截取外部副作用发生前的一瞬间。

推理：这个切口同时具备明确标签、清楚时序和可执行干预窗口；一旦动作执行，日志虽更完整，却失去预防价值。

判断：agent interpretability 不一定要先解决“理解所有 reasoning”。优先找能阻断高代价错误的窄 decision boundaries，可能更快产生实际安全收益。

6.2 最合理的产品形态是 dense detector + sparse explanation sidecar

观察：RAW 在 held-out Nemotron 全面更准，SAE 的优势是可定位与可命名。

推理：强行让同一个 representation 同时负责最高召回和最好解释，没有实验依据。

判断：部署时可让 calibrated dense probe 负责第一层告警，仅对告警样本运行 SAE sidecar 生成 layer/feature evidence；再用独立 policy 决定 review、sandbox 或 approval。这样把 detection、explanation 与 control 三个目标分开优化。

6.3 Tool-Need 比 Tool-Risk 更接近可迁移机制

Tool-Need 问的是通用的“内部知识是否足以继续”，跨工具 namespace 仍有相对稳定语义；Tool-Risk 却依赖组织权限、arguments 和环境。论文中 Tool-Need 在 BFCL 仍有信号，而 risk transfer 更弱，不只是数据量问题，也是 target 定义不同。后续工作应把 Tool-Risk 从静态分类改成 context-conditioned policy evaluation。

7. 必须记住的五点

  1. 论文监控的是 pre-action tool-decision boundary，不是完整 agent cognition。
  2. 最后 32 个 tokens 的多层 residual 经 SAE 编码，再由 Tool-Need / Tool-Risk 线性 probes 读出。
  3. RAW probe 预测更强；SAE 交换来 sparse inspectability，论文尚未证明这种可检查性改善人类审计。
  4. 最强 runtime 证据是 probe 提前标记约 75.5% 的 missed tool calls。
  5. feature ablation 只因果影响 probe readout；要解释真实 agent policy，仍需 generation-time intervention。

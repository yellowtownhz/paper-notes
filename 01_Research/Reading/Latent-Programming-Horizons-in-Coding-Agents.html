论文笔记: Latent Programming Horizons in Coding Agents

1. 背景信息

  • 作者 / 团队：André Silva、Han Tu、Martin Monperrus；KTH Royal Institute of Technology
  • 发表：arXiv preprint v1，2026-07-06（cs.LG / cs.SE），尚无会议录用信息
  • 代码：https://github.com/ASSERT-KTH/program-probes
  • 数据：https://huggingface.co/datasets/ASSERT-KTH/latent-programming-horizons-trajs

先给结论。 这篇论文最扎实的发现是：coding agent 工作时的 residual stream 确实含有可被线性探针读出的程序状态信号，而且 correctness / regression 这类语义属性比语法合法性更容易读出，最高 AUC 为 0.841（Table 5）。更吸睛的“25-step latent programming horizon”也是真实观测到的相关性，但目前还不能直接解释成 agent 在内部提前规划了 25 步：这里的 step 是 agent 交互轮次，不是代码 edit；标签在两次 edit 之间原样沿用，而一条 trajectory 的 edit 次数中位数只有 2（Table 1）。

2. 关键问题：agent 在多轮改代码时，内部是否维护了一个程序状态？

此前的 correctness probing 主要研究单次函数生成：完整代码就在上下文中，模型只生成一次，程序状态也不会变化。真正的 coding agent 不一样：它只看到部分代码库，连续几十步读文件、编辑、运行测试，再根据反馈修正。我们不知道模型内部到底是在维护“当前程序是什么样”，还是只在局部地响应最新一段文本。

Golden Case — 论文 Figure 1 的示意案例（不是实测 trajectory）。

用户要求修复 “nested generics 无法解析”。agent 先读 lexer.py，第一次 edit 增加括号深度跟踪，测试仍有 1 个失败；第二次 edit 修复最深层嵌套，最后 3 个测试全部通过。

外部观察只能看到 read → edit → test → edit → test。论文追问的是：在第一次 edit 还没发生时，模型当时的 hidden state 是否已经包含“这条路线最终会让程序可解析 / 通过测试”的信息？如果能从 hidden state 读出当前代码属性，这是 latent program representation；如果还能读出未来第 $k$ 步程序的属性，作者称之为 latent programming horizon。

这个问题值得研究有两个原因：

  1. 解释层面：如果 agent 持续维护程序语义，coding LLM 更像一个更新中的 world model，而不只是局部 next-token predictor。
  2. 工程层面：若 correctness / regression 能在 edit 写入磁盘前被读出，就可能做内部监控、提前预警，甚至 activation steering。

但 “hidden state 可预测某个标签” 和 “模型拥有一个独立于表面文本、且因果参与决策的程序模型” 不是同一件事，这正是本文证据需要被审查的地方。

3. 关键方法：把每次 edit 后的真实程序属性对齐到 residual stream，再训练不同 horizon 的线性探针

3.1 沿 Golden Case 跑一遍

  1. mini-swe-agent 接收 issue，逐步输出读文件、编辑和测试动作；完整轨迹是：

    $$ \mathcal{T}=C_1\oplus A_1\oplus O_1\oplus\cdots\oplus A_S\oplus O_S, $$

    其中 $A_s$ 是第 $s$ 步 agent 输出，$O_s$ 是工具返回。

  2. 每当工具调用修改代码库，作者保存当时的程序版本并在外部重新运行解析器 / 编译器和测试，得到四个二元标签。以示意案例为例，第一次 edit 后可能是“可解析但未完全正确”，第二次 edit 后变为“可解析且完全正确”。

  3. 从 agent 生成部分每隔 5 个 token 抽取 residual-stream vector $\mathbf h_t^\ell$，检查第 $\ell\in\{1,11,21,31,40\}$ 层。

  4. 对每个“属性 × 层 × horizon”单独训练 logistic-regression probe。当前状态探针用 $k=0$；未来探针用：

    $$ \hat y^{\phi}_{\sigma(t)+k}=\operatorname{probe}(\mathbf h_t^\ell), $$

    即仅用位置 $t$ 的 activation，预测第 $k$ 个 agent step 之后的程序属性 $\phi$。

  5. train / validation / test 按 task identifier 划分，同一任务的不同 rollout 不会跨 split。控制组把标签随机打乱后重训同结构探针；若它回到 AUC 0.5，说明正常探针并非仅靠容量记住随机映射。

3.2 四个程序属性如何定义

属性 正标签定义 它回答的问题
Well-formedness 当前版本可 parse / compile edit 至少能运行吗？
Full correctness 通过 benchmark 全部测试 oracle 问题已经真正解决吗？
Partial correctness 失败测试数严格少于任务开始时 是否在往正确方向走？
Regression 原先通过的任一测试现在失败 是否破坏了已有行为？

这里最关键、也最容易漏掉的实现细节是：ground-truth 只在 edit event 上重新计算；一次 edit 后的标签会被赋给直到下一次 edit 之前的所有生成位置。于是模型运行测试、阅读文件或思考时，label 仍描述“最近一次 edit 后的程序版本”。

3.3 数据与控制变量

  • Agent scaffold：mini-swe-agent v2.2.8；每条 trajectory 最多 100 steps，tool timeout 180 秒，context 256k。
  • 模型：Laguna-XS.2 与 Qwen3.6-35B-A3B，均为 hidden dimension 2048 的 open-weight 模型；检查第 1/11/21/31/40 层。
  • Benchmark：SWE-Bench-Verified 全部 500 个任务；SWE-Bench-Pro 全部 731 个任务。每个任务尝试最多 10 条 trajectory。
  • 总规模：22,714 条 trajectory、79,480 次 edit、22.4M 个 hidden-state vectors；trajectory step 中位数 52，但 edit 中位数仅 2、均值 3.5（Table 1）。
  • 长 horizon 子集：$k\leq 50$ 实验只保留至少 50 steps 的 12,183 条 trajectory，并剔除每条轨迹末尾 50 steps，以保证不同 $k$ 使用相同 token population；Appendix Figure 9/11/13/15 另用 $k\leq15$ 在更完整样本上复现趋势。

3.4 与已有 correctness probe 的实质区别

新增的不是 probe 结构——它仍是低容量线性分类器——而是动态真实代码库 + 多轮 agent trajectory + 未来 step 标签：程序状态会随 edit 改变，模型只通过工具逐步观察代码库，标签来自真实编译 / 测试结果，而不是单次生成代码的静态 correctness。

4. 关键结果：当前状态信号很强；“未来状态”信号存在，但规划解释尚未被控制实验锁定

4.1 当前程序属性在 hidden state 中线性可读

要验证什么：探针能否从 residual stream 恢复最近一次 edit 后的真实程序属性，而不是对随机标签过拟合？

观察（Table 5 / Figure 3）：

Model / Benchmark Full correctness 最佳 AUC Partial correctness 最佳 AUC Regression 最佳 AUC Shuffled control
Laguna / Verified 0.727 (L21) 0.708 (L21) 0.678 (L21) 0.500–0.501
Laguna / Pro 0.732 (L21) 0.722 (L21) 0.745 (L31) 0.500–0.501
Qwen3.6 / Verified 0.828 (L31) 0.808 (L31) 0.721 (L21/L31) 0.501
Qwen3.6 / Pro 0.832 (L31) 0.841 (L21) 0.792 (L21) 0.502–0.507

Well-formedness 是明显例外：在几乎全是可解析 Python 程序的 Verified 上正标签率为 0.93–0.94，AUC 仅 0.57–0.59；换到包含 C++、TypeScript 等更多语法失败的 Pro，AUC 升至 0.74–0.78（Figure 3、Appendix Figure 7）。这不是“语法比语义更难”，而主要是标签分布不同。

能说明什么：residual stream 与当前程序 correctness / regression 存在稳定、线性可访问的统计关系；随机标签控制说明信号确实来自正常 activation 与真实标签的对应关系。

还不能说明什么：activation 里包含任务描述、此前读到的源码、测试命令和测试输出。论文没有 text-only baseline，也没有把“测试结果已经明确出现在上下文之后”的 token 与之前分开。因而 probe 可能部分读到表面 trajectory 信号（例如 3 passed），尚不能证明模型维护了一个独立于文本的完整程序语义模型。

4.2 程序属性信号集中在中间层

Figure 4 / Table 5 基本呈 inverted-U：L1 最弱，L21/L31 最强，L40 略回落；除 well-formedness 外，这一层序在两个模型、两个 benchmark 上都很稳定。作者的解释是：浅层尚未形成抽象语义，末层更贴近 next-token 输出，中间层保留最可读的程序属性。

这里的证据适合支持“在哪里最容易读出”，不等于证明属性只存储在中间层。linear probe 的可读性还受表示基底、尺度和线性化程度影响。

4.3 语义探针跨 benchmark 迁移，但语法探针不行

设置：直接把 Verified 上训练的 probe 用于 Pro，反向亦然，不重训（Figure 5 / Table 6）。

结果：Full / Partial correctness 在最佳层的 transfer AUC 为 0.63–0.78，相比各自 evaluation set 上的 in-distribution AUC 下降约 0.04–0.09。Well-formedness 则大多接近随机，因为 Verified 几乎恒为 syntactically valid，而 Pro 的语言和失败率分布不同。

判断：语义信号不是某个 benchmark 独有的标签映射，这是不错的 external-validity 证据；但两个数据集仍共享 SWE-bench 式 issue resolving、同一 agent scaffold 和相似测试反馈文本，所以它还不是跨 agent / 跨工作流的普适性证明。

4.4 “latent programming horizon”：AUC 在前 25 steps 快速衰减，之后仍略高于随机

设置：用当前 $\mathbf h_t^\ell$ 预测第 $k\in[0,50]$ 个 agent step 之后的标签；Figure 6 展示 Laguna 的 Full / Partial correctness。

结果（Section 4.2 / Figure 6）：

  • Full correctness 在 $k=0$ 时约为 0.77（Verified）/ 0.82（Pro）；
  • 到 $k\approx25$ 时降至约 0.55 / 0.65；
  • 到 $k=50$ 后平台仍约为 0.52 / 0.60，高于 0.50；
  • $k\leq15$ 的大样本复现实验仍看到随 $k\to0$ 单调上升的 hockey-stick 曲线（Appendix A.4）。

这支持“当前 activation 对未来 trajectory outcome 有信息”。但作者把它进一步解释为“agent 提前表示了未来程序”，证据还差一个关键控制：k 是交互 step，不是 edit index；标签又在 edit 之间 carry forward。 数据中 52-step trajectory 只有 2 次 edit（中位数），所以不少 $(t,t+k)$ 很可能仍对应同一个程序版本。即使跨过了 edit，current label、任务难度、最终能否解决的整体 propensity 也可能预测 future label。

要把 horizon 解释锁定为真正的 look-ahead，至少需要：

  1. 只评估中间确实跨过一次或多次 edit 的样本，并用“第 $k$ 次未来 edit”而不是“第 $k$ 个 agent step”定义 horizon；
  2. 加入 current label persistence、step position、task metadata / difficulty、trajectory text-only 等 baseline；
  3. 在同一文本可见信息下比较不同 future outcome，或仅使用尚未出现测试反馈的 activation；
  4. steering probe direction 并观察未来 edit 是否因果改变。

因此我会把本文最强结论写成：coding-agent activation 能提前预测未来程序属性；它是否代表显式、多步的内部编程计划，仍未被证明。

5. Insights

5.1 对论文本身的 Comments

“真实程序 oracle + 多轮 trajectory” 是这篇最有价值的实验资产。 之前的 probe 容易停留在 isolated snippet；这里每个 edit 都重新 checkout 代码并跑编译 / 测试，将 activation 对齐到真实软件状态。22,714 条 trajectory 和跨 task split 让“当前状态可读”这部分比标题里的 horizon 更可信。

论文的标题主张强于它的控制实验。 shuffled-label control 只能排除“线性分类器凭容量拟合随机标签”，不能排除 probe 从测试日志、当前标签持久性或 task difficulty 读取捷径。特别是 median 52 steps 对 median 2 edits 的反差，使 “25-step” 听起来比实际程序状态变化更长。最关键的补实验不是再加模型，而是把 x 轴从 agent step 改成 edit event，并报告 persistence baseline。

作者对 decodability ≠ causality 的限定是正确的，但还应再退一步：decodability 也不自动等于 latent program model。 hidden state 是整个上下文的压缩，其中包含源码、自然语言计划和测试回显。需要“相同 surface evidence、不同 program property”的对照，才能证明 probe 读到的是程序语义而不只是文本痕迹。这与 activation-oracle 工作中的 text-inversion 问题本质相同。

5.2 对实际工作的启发

在现有证据下，最合理的工程用途是只读 risk monitor：从中间层实时估计 regression / correctness 风险，在风险升高时要求 agent 运行更完整的测试或重新审查 edit。直接用 probe 做 steering 还太早，因为 probe direction 未被证明是 agent 决策所使用的因果变量，而且跨模型无法直接复用。

一个值得复现的最小实验是：在相同 task、相同已见上下文、尚未执行测试的位置训练 regression probe，再与 text-only classifier 和 current-label persistence 比较；若 activation probe 仍显著领先，才说明它提供了部署上真正新增的早期信号。

5.3 研究品味

这篇论文展示了一个很好的问题生成方式：把已经在 chess / reasoning 中成立的 “future state 可读出” 迁移到 coding agent，并为连续代码版本定义可执行 oracle。它同时也提醒我们，漂亮概念（latent programming horizon）必须和 measurement unit 对齐；当“step”与真正改变研究对象的“edit”不是同一个单位时，概念命名会自然诱导过度解释。
